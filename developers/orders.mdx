Order endpoints require API key authentication. See [Authentication](/developers/authentication) for HMAC signing.

## Order Model

Hit accepts low-level order payloads built from outcome token amounts.

| Field | Required | Description |
| --- | --- | --- |
| `salt` | Yes | Unique numeric string |
| `taker` | Yes | Usually `0x0000000000000000000000000000000000000000` |
| `tokenId` | Yes | Outcome token ID from market data |
| `makerAmount` | Yes | Amount supplied by the maker, in 6-decimal base units |
| `takerAmount` | Yes | Amount requested from the taker, in 6-decimal base units |
| `expiration` | Yes | Unix timestamp seconds, or `0` |
| `side` | Yes | `0` for buy, `1` for sell |
| `orderType` | Yes | `GTC`, `FOK` or `FAK` |
| `feeRateBps` | Client-signed only | Must match the market `orderFeeRateBps` |
| `signature` | Optional | Include for client-signed orders; omit when using server-side session signer |
| `idempotencyKey` | Optional | UUID v4 used to deduplicate repeated submission of the same logical order |
| `postOnly` | Optional | Maker-only GTC order; rejected if it would cross the book |

Do not send `priceUint`. The server sets it, and the request validator rejects a body that carries it.

Amounts use 6 decimals:

```text
1 USDC = 1000000
1 share = 1000000
```

For limit orders:

| Side | Meaning |
| --- | --- |
| Buy (`side: 0`) | `makerAmount` is USDC, `takerAmount` is shares, price = `makerAmount / takerAmount` |
| Sell (`side: 1`) | `makerAmount` is shares, `takerAmount` is USDC, price = `takerAmount / makerAmount` |

Limit order prices must be valid multiples of the market `tickSize`.

### Client-Signed Orders

Sign over your account's identity. After your account's upgrade, maker and signer are both your wallet and the signature type is `0`. Before it, the maker is your old wallet address, the signer is your wallet, and the signature type is `2`. `maker`, `signer`, `signatureType` and `nonce` are part of the signed message but are not sent in the body: Hit sets them from your account. See [Place a Client-Signed Order](#place-a-client-signed-order).

### Account Upgrades

While your account's wallet is being upgraded, `POST /orders` and `POST /orders/batch` answer `409` with `errorCode: "wallet-migration-in-progress"`. This applies whether you sign orders yourself or Hit signs them for you. The upgrade also cancels your resting orders and closes your `/user` WebSocket connection.

1. Treat the `409` as retryable: back off and re-send.
2. When the socket closes, reconnect, authenticate and subscribe again.
3. Once orders are accepted again, read your open orders and replace the quotes that were cancelled.

If you sign orders yourself, call `GET /markets/value` again before you sign, as your maker and signature type change.

import { createHmac, randomBytes } from "node:crypto";

type JsonObject = Record<string, unknown>;

function units(value: number) {
  return Math.round(value * 1_000_000).toString();

function sign(secret: string, timestamp: string, method: string, path: string, body = "") {
  return createHmac("sha256", secret)

    .digest("hex");

      "hit-timestamp": timestamp,
      "hit-passphrase": process.env.HIT_API_PASSPHRASE!,
    },
    body: bodyText || undefined,
  });

  if (!response.ok) {
    throw new Error(`${response.status}: ${await response.text()}`);
  }

  return response.json() as Promise<unknown>;
}

use hmac::{Hmac, Mac};
use reqwest::blocking::Client;
use serde_json::{json, Value};
use sha2::Sha256;
use std::env;
use std::time::{SystemTime, UNIX_EPOCH};

type HmacSha256 = Hmac<Sha256>;

fn timestamp_ms() -> String {
    SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .expect("system clock before unix epoch")
        .as_millis()
        .to_string()
}

fn units(value: f64) -> String {
    (value * 1_000_000.0).round().to_string()
}

fn sign(secret: &str, timestamp: &str, method: &str, path: &str, body: &str) -> String {
    let message = format!("{}{}{}{}", timestamp, method.to_uppercase(), path, body);
    let mut mac = HmacSha256::new_from_slice(secret.as_bytes()).expect("hmac accepts any key");
    mac.update(message.as_bytes());
    hex::encode(mac.finalize().into_bytes())
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = Client::new();
    let path = "/api/v1/orders";
    let timestamp = timestamp_ms();
    let payload = json!({
        "salt": rand::random::<u128>().to_string(),
        "taker": "0x0000000000000000000000000000000000000000",
        "tokenId": env::var("HIT_TOKEN_ID")?,
        "makerAmount": units(31.0),
        "takerAmount": units(50.0),
        "expiration": 0,
        "side": 0,
        "orderType": "GTC"
    });
    let body = serde_json::to_string(&payload)?;
    let signature = sign(&env::var("HIT_API_SECRET")?, &timestamp, "POST", path, &body);

    let order: Value = client
        .post(format!("https://hit.com{}", path))
        .header("Content-Type", "application/json")
        .header("hit-api-key", env::var("HIT_API_KEY")?)
        .header("hit-signature", signature)
        .header("hit-timestamp", timestamp)
        .header("hit-passphrase", env::var("HIT_API_PASSPHRASE")?)
        .body(body)
        .send()?
        .error_for_status()?
        .json()?;

    println!("{order:#}");
    Ok(())
}

## Place a Client-Signed Order

To sign orders yourself:

1. Call `GET /markets/value` without `user`. The returned `user` is the `maker` to sign with. If it is your wallet's address, sign with signature type `0` and your wallet as `signer`. If it is a different address, your account has not been upgraded yet: sign with signature type `2`, that address as `maker` and your wallet as `signer`.
2. Read the market with `GET /markets/{id_or_slug}` and pick the exchange from the market's `negRisk`, not the event's: the neg-risk exchange when it is `true`, the standard exchange otherwise.
3. Sign the complete EIP-712 `Order` with nonce `0`, using your wallet's private key.
4. Send the order with API key authentication.

The signed message and the request body are not the same set of fields:

| Field | Signed message | `POST /orders` body |
| --- | --- | --- |
| `salt`, `taker`, `tokenId`, `makerAmount`, `takerAmount`, `expiration`, `feeRateBps`, `side` | Yes | Yes, with the same values |
| `maker`, `signer`, `signatureType` | Yes | No. Sending them returns `400` |
| `nonce` | Yes, always `0` | No |
| `signature` | No | Yes |
| `orderType`, `postOnly`, `idempotencyKey` | No | Yes |

The examples add to the `request` and `units` helpers from [Place an Order](#place-an-order). Set `HIT_MARKET_ID` to the market and `HIT_WALLET_PRIVATE_KEY` to the private key of your HIT Wallet. Keep the key secret: anyone who has it controls your funds.

| EIP-712 domain | Value |
| --- | --- |
| `name` | `Metawin CTF Exchange` |
| `version` | `1` |
| `chainId` | `8453` (Base) |
| `verifyingContract` | The exchange the order goes to: standard `0x71aCeb0c45f4d58a2549Dd21F1aDc8E86d2899EA`, neg-risk `0xDf667F94322fEcCa5D56a72Bb21a8a418b5EaC94` |

The same exchange addresses are also served by `GET /api/v1/contracts`.

A signed order whose nonce is not your wallet's current nonce on that exchange is refused with `400` and `errorCode: "nonce-stale"`. The nonce only moves if your wallet itself calls `incrementNonce()` on the exchange. After that, client-signed orders on that exchange cannot succeed, and this is terminal today: send orders without a `signature` so Hit signs them for you. A `nonce` field to recover from this is planned.

## Taker Delay

Some markets hold marketable orders for a short delay before matching. An order is marketable when it would match against an order already on the book, which makes it a taker order. Orders that rest on the book without matching are not delayed.

Read the delay for any market from its `speedBumpDelayMs` field in [market data](/developers/market-data).

| Markets | Delay |
| --- | --- |
| Short-dated up/down markets | 250ms |

Read `speedBumpDelayMs` rather than hard-coding these values. The table shows where delays apply today, and more market types may get one in future.

You cannot cancel an order while it is delayed. On the `/user` WebSocket namespace, an `order-speed-bump-pending` event tells you an order was delayed before matching. See [WebSockets](/developers/websockets#events).

## Retrying a Failed Order

`POST /orders` answers `503` when your order could not be signed, submitted or admitted. Nothing is created when it does, so re-sending the identical body cannot duplicate the order. Each of these `503`s carries a `Retry-After` header and repeats the same figure in the body as `retryAfterSeconds`.

A `503` whose `error` is `CREDENTIAL_UNVERIFIABLE` is not one of them. Your API key could not be checked, so the order was not attempted. It carries no `Retry-After` header: re-send the request, signed again with a fresh `hit-timestamp`. See [Authentication Failures](/developers/authentication#authentication-failures).

Read `error` before `errorCode`. It is the discriminator, and only one of its two values carries an `errorCode` at all.

`SIGNING_UNAVAILABLE` has no `errorCode`. It has four causes: the signing provider being unavailable, rate-limiting Hit or having no slot in Hit's signing-admission queue; the request budget being exhausted before your order was submitted; the duplicate guard's store being unavailable; and, on `POST /orders/batch` only, the locking infrastructure being unavailable. Three of those four — the request budget, the duplicate guard's store, and the batch locking infrastructure — reach orders you signed yourself, so do not treat this status as something that only happens to orders Hit signs for you. Every batch takes its per-account lock whether or not anything in it needs signing.

`ORDER_ADMISSION_UNAVAILABLE` carries an `errorCode`, one of six values:

| `errorCode` | Meaning |
| --- | --- |
| `projection-stale` | The balance projection is not committing. |
| `balance-unknown` | Your balance has not been read from chain yet. |
| `balance-unprojected` | You have no projection row. |
| `collateral-source-unavailable` | The projection could not be queried at all. |
| `engine-busy` | The venue declined to admit the command at all. |
| `idempotency-unverifiable` | The venue could not check whether the idempotency key derived from your order had already been used. |

The first four mean your collateral could not be read. `engine-busy` is a stronger statement than the others: the command was not decided, not recorded and not partially applied, because the venue was at one of its own internal bounds. `idempotency-unverifiable` means the duplicate check could not be answered, so the venue refused rather than risk a second live order for one key.

<Warning>
  When you retry `engine-busy` or `idempotency-unverifiable`, re-send the identical body
  and do not change `salt`. The idempotency key is derived from the order's contents, so a
  new salt is a different order and defeats the deduplication these codes exist to protect.
</Warning>

None of these means your order is invalid or your balance is insufficient. A genuinely insufficient balance is a `400`, and retrying it will not help.

`POST /orders/batch` reports the same six reasons per entry rather than as a `503`. They arrive as that entry's `code` inside a normal `201`, with no `Retry-After` header, because other entries in the same request may have been created. That per-entry `code` set is open-ended: it is whatever the venue supplies for the entry, plus local fallbacks such as `bad-request`, `internal-error`, `not-attempted`, `nonce-stale` and `order-archived`. Do not assume the list is closed, and treat a value you do not recognise the way you treat `internal-error`. The batch route can still answer a request-level `503` with `error: "SIGNING_UNAVAILABLE"`, and then nothing in the batch was created.

## List Orders

```bash
curl 'https://hit.com/api/v1/orders' \
  -H 'hit-api-key: API_KEY' \
  -H 'hit-signature: SIGNATURE' \
  -H 'hit-timestamp: TIMESTAMP' \
  -H 'hit-passphrase: API_PASSPHRASE'
```

Filters:

| Query | Description |
| --- | --- |
| `market` | Market UUID |
| `status` | `PENDING`, `EXECUTING`, `EXECUTED` or `REJECTED`; use the paginated endpoint for `CANCELLED` |
| `maker` | Maker wallet address |
| `marketName` | Case-insensitive partial market name |
| `sortBy` | Order sort field, default `created_at` |
| `order` | `ASC` or `DESC` |

When `status` is omitted, `GET /orders` returns all non-cancelled statuses. Passing `status=CANCELLED` returns `400`.

Use `GET /orders/paginated` for paginated results and cancelled history. Its omitted-status default is active orders only (`PENDING` and `EXECUTING`). `total` is opt-in and capped; use `cursor`, `hasMore` and `nextCursor` for efficient deep pagination.

Your own writes are already visible to these reads. A create or cancel this API has acknowledged appears on your next `GET /orders`, `GET /orders/paginated` or `GET /orders/{id}`, so you do not need to poll until it shows up or sleep between writing and reading. The read waits for the read model to catch up, bounded at 1 second by default. If that bound expires you still get an answer, built from what has been written so far, which may be missing your most recent write; re-read in that case rather than re-sending the write. `GET /orders/events` reads a different table and is outside this guarantee.

## Cancel Orders

| Request | Description |
| --- | --- |
| `POST /orders/{id}/cancel` | Cancel one order and return the updated order |
| `POST /orders/batch-cancel` | Cancel up to 50 order IDs |
| `POST /orders/cancel` | Cancel all orders in one market |
| `POST /orders/cancel-event` | Cancel all your orders across every market in one event |
| `POST /orders/cancel-all` | Cancel all your orders |

Cancel one order:

```typescript
await request("POST", `/orders/${process.env.HIT_ORDER_ID!}/cancel`);
```

Cancel a batch:

```typescript
await request("POST", "/orders/batch-cancel", {
  orderIds: ["ORDER_UUID_1", "ORDER_UUID_2"],
});
```

Cancel all orders in a market:

```typescript
await request("POST", "/orders/cancel", {
  market: "MARKET_UUID",
});
```

Cancel all orders in an event:

```typescript
await request("POST", "/orders/cancel-event", {
  eventId: "EVENT_UUID",
});
```

Cancellations fail in different shapes depending on the route:

| Request | Failure to handle |
| --- | --- |
| `POST /orders/{id}/cancel`, `POST /orders/cancel` | `503` with `error: "ORDER_ADMISSION_UNAVAILABLE"`, `errorCode: "engine-busy"` and a `Retry-After` header |
| `POST /orders/batch-cancel` | `500`, `408`, `503` or `409`, each with its own meaning |
| `POST /orders/cancel-all`, `POST /orders/cancel-event` | `207` when any order is still resting, `503` with an `outcome`, `409` or `422`, and unsuccessful entries in `results` |

A `503` from `POST /orders/{id}/cancel` or `POST /orders/cancel` means nothing was cancelled, and you can re-send the identical request.

On every one of these routes, a `503` whose `error` is `CREDENTIAL_UNVERIFIABLE` means your API key could not be checked and the request was not attempted, so nothing was cancelled. It carries no `Retry-After` header. Re-send the request, signed again with a fresh `hit-timestamp`.

`POST /orders/batch-cancel` takes 1 to 50 version-4 UUIDs. It answers `500` when the venue replied with an error, `408` when no reply arrived within 30 seconds, `503` when the message broker failed, and `409` when another cancel-shaped batch is already in flight. None of the first three carries a `Retry-After` header or an `errorCode`. `408` and the broker's `503` are lost-response cases: the orders may or may not have been cancelled, so re-read them before re-issuing. `409` is usually plain contention, but it is also returned when the lock service fails after your cancel was already published, so re-read on that one too rather than assuming nothing happened.

`POST /orders/cancel-all` and `POST /orders/cancel-event` answer `200` when every order in scope is off the book and `207` when at least one is still resting. Both statuses carry the same body, so test for a 2xx rather than for one status. Read `results`, which has one entry per order the request covered. `success` says whether this request cancelled the order, so an entry can be `false` for an order that was already filled or cancelled. Decide from `code`:

```typescript
type CancelResult = { orderId: string; success: boolean; code?: string; error?: string };

const { results } = (await request("POST", "/orders/cancel-all")) as { results: CancelResult[] };

const alreadyGone = ["state-conflict", "not-found"];

for (const entry of results) {
  if (entry.success || alreadyGone.includes(entry.code ?? "")) {
    continue; // off the book: nothing of yours is resting
  }
  if (entry.code === "unknown") {
    // The venue cannot say whether this cancel took effect. Read your open orders before re-sending.
    console.log("check", entry.orderId);
  } else {
    // Still resting: not-attempted, engine-busy, or a failure with no code.
    console.log("resting", entry.orderId);
  }
}
```

The `request` helper above returns only the body, and throws on any status that is not a 2xx. To tell `200` from `207`, read `response.status` in your own helper before parsing the body. If a `207` carries no entry that is still resting, read your open orders before re-sending.

A `503` whose `error` is `ORDER_SERVICE_UNAVAILABLE` carries an `outcome`: `nothing-cancelled` means the request never started and can be re-sent as it is; `unknown` means it may or may not have cancelled, so read your open orders first. One cause of `nothing-cancelled` is that the sweep could not read its list of your orders (order reads at capacity, no database connection free in time, or no way to confirm the list includes every order you were acknowledged for), so it acted on none of them. That `503` and the `ORDER_ADMISSION_UNAVAILABLE` one described under [Admission Errors](/api-reference/orders#admission-errors) can both still carry `results` for orders the venue reached before the failure.

### Migrating from the market fields

The cancel-all and cancel-event responses used to carry five market-level fields beside `results`: `clearedMarkets`, `failedMarkets`, `notAdmitted`, `markets` and `cancelled`. **These fields were removed in `markets-v0.0.149`.** The response now carries `results` alone, so a client that still reads any of those fields finds them absent. Read `results` and the status instead.

| If you read | Read instead |
| --- | --- |
| `failedMarkets`, to decide what to retry | The entries in `results` that are still resting, as in the example above. Re-send for those, and read your open orders first for any marked `unknown`. |
| `notAdmitted`, for markets the venue refused | Entries in `results` with `code: "engine-busy"`. They carry no `retryAfterSeconds`. |
| `clearedMarkets`, `markets` or `cancelled`, to confirm the cancel worked | The status. `200` means every order in scope is off the book. |
| A `201` status, as success | Any 2xx. These routes answer `200` or `207`, not `201`. |

`results` entries carry no market ID. If you need to know which market an order was in, use your own order records or `GET /orders/{id}`.

Full response shapes are in the [Orders API reference](/api-reference/orders#cancel-sweep-response).

## Positions and Activity

These endpoints also accept API key authentication:

| Request | Description |
| --- | --- |
| `GET /markets/user-positions` | Current user positions |
| `GET /markets/value` | Position value for the current user, or for the wallet address in `user`. Called without `user`, the returned `user` is the `maker` to sign orders with. A supplied `user` only returns that address's valuation and is not a signing identity |
| `GET /markets/user-activity` | User activity feed |
| `GET /markets/traded-count` | Number of markets traded |
| `GET /markets/redeemable-positions` | Resolved markets with positions you can redeem |
| `POST /markets/redeem-positions/batch` | Redeem one or more resolved market positions |
| `GET /markets/mergeable-positions` | Active markets where you hold both outcome legs |
| `POST /markets/merge-positions/batch` | Merge one or more complete Yes/No sets back into collateral |
| `GET /orders/events` | Active order book events across the platform, not scoped to you |
