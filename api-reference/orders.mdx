---
title: Orders
description: Order listing, creation and cancellation endpoint reference
---

Reads are consistent with your own writes: a create or cancel this API has acknowledged is visible on your next `GET /orders`, `GET /orders/paginated` or `GET /orders/{id}`, so you do not need to poll until it appears or sleep between writing and reading. Those reads wait for the read model to catch up, bounded at 1 second by default. If that bound expires the request is still answered, with what has been written so far, which may be missing your most recent write; re-read rather than re-sending the write. `GET /orders/events` reads a different table and is outside this guarantee.

## List Orders

```text
GET /api/v1/orders
```

**Authentication:** `API key HMAC`

Query parameters:

| Query | Type | Required | Description |
| --- | --- | --- | --- |
| `market` | UUID string | No | Market UUID. |
| `status` | enum string | No | `PENDING`, `EXECUTING`, `EXECUTED` or `REJECTED`. `CANCELLED` is rejected; use `/orders/paginated`. |
| `maker` | address string | No | Maker address. Matched case-insensitively, so a checksummed address works. |
| `marketName` | string | No | Case-insensitive partial market name. |
| `sortBy` | enum string | No | `created_at`, `total`, `amount` or `filled`. Default `created_at`. |
| `order` | enum string | No | `ASC` or `DESC`. Default `DESC`. |

Response type: `OrderWithMarket[]`.

When `status` is omitted, the endpoint returns all non-cancelled statuses. Passing `status=CANCELLED` returns `400`.

## Create Order

```text
POST /api/v1/orders
```

**Authentication:** `API key HMAC`

Request body type: `CreateOrder`.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `salt` | string | Yes | Unique uint256 numeric string. Max 78 characters. |
| `taker` | address string | Yes | Taker address. Use the zero address for open GTC maker orders. |
| `tokenId` | string | Yes | Outcome token ID as a numeric string. Max 78 characters. |
| `makerAmount` | string | Yes | Positive integer string in base units. Max 78 characters. |
| `takerAmount` | string | Yes | Positive integer string in base units. Max 78 characters. |
| `expiration` | integer | Yes | Unix timestamp in seconds, or `0`. |
| `feeRateBps` | integer | No | Fee rate in basis points. Range `0` to `10000`. |
| `side` | integer | Yes | `0` buy, `1` sell. |
| `signature` | string | No | Client-side EIP-712 order signature. |
| `orderType` | enum string | Yes | `GTC`, `FOK` or `FAK`. |
| `postOnly` | boolean | No | Maker-only flag. Valid for GTC only; a crossing post-only order is rejected. Default `false`. |
| `priceUint` | string | No | Server-compatible price integer. |
| `idempotencyKey` | UUID v4 string | No | Client key for deduplicating repeated submission of the same logical order. |

Response type: `Order`.

This endpoint returns `503` when the order could not be signed, submitted or admitted. Every `503` here means nothing was created, so re-sending the identical body cannot duplicate the order. See [Admission Errors](#admission-errors). An insufficient balance is a `400`, not a `503`, and retrying it will not help.

## Create Batch Orders

```text
POST /api/v1/orders/batch
```

**Authentication:** `API key HMAC`

Request body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `orders` | `CreateOrder[]` | Yes | Orders to create. Minimum `1`, maximum `50`. |

Response type: `CreateBatchOrdersResponse`.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `results` | `BatchOrderResult[]` | Yes | Per-order results in request order. |

`BatchOrderResult`:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `index` | integer | Yes | Index of the order in the submitted batch. |
| `success` | boolean | Yes | Whether that order was created. |
| `orderId` | UUID string | No | Created order UUID when successful. |
| `hash` | string | No | EIP-712 hash of the created order when `success` is true, lowercase `0x`-prefixed. The same value the order's WebSocket events and `GET /orders` carry. If you signed the order yourself, compare it with the order you submitted at `index`. |
| `code` | string | No | Machine-readable reason when unsuccessful. |
| `error` | string | No | Error message when unsuccessful. |

The six `errorCode` values listed under [Admission Errors](#admission-errors) arrive on this route as an entry's `code` inside a normal `201`, with no `Retry-After` header, because other entries in the same request may have been created. The `code` set is open-ended: it is whatever the venue supplies for that entry, plus local fallbacks including `bad-request`, `internal-error`, `not-attempted`, `nonce-stale` and `order-archived`. Do not assume the set is closed; treat an unrecognised `code` the way you treat `internal-error`.

This route can still answer a request-level `503` with `error: "SIGNING_UNAVAILABLE"`, in which case no order in the batch was created.

## Cancel Batch Orders

```text
POST /api/v1/orders/batch-cancel
```

**Authentication:** `API key HMAC`

Request body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `orderIds` | UUID v4 string[] | Yes | Version-4 order UUIDs to cancel. Minimum `1`, maximum `50`. |

Response type: `BatchCancelOrdersResponse`.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `results` | `BatchCancelOrderResult[]` | Yes | Per-order cancellation results. |

`BatchCancelOrderResult`:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `orderId` | UUID string | Yes | Order UUID. |
| `success` | boolean | Yes | Whether the order was cancelled. |
| `error` | string | No | Error message when unsuccessful. |
| `code` | string | No | Machine-readable failure class when unsuccessful. Branch on this rather than matching `error`. `not-attempted` means the batch stopped before reaching this order, so it was not touched and re-submitting its cancel is safe. |

A failed reply is returned as its own status rather than collapsed into a `409`:

| Status | Meaning |
| --- | --- |
| `500` | The venue answered with an error. |
| `408` | No reply within 30 seconds. |
| `503` | The message broker failed. |
| `409` | Another cancel-shaped batch is already in flight, or the lock service failed after your cancel was already published. In the second case the orders may already be cancelled, so re-read them rather than assuming nothing happened. |

None of these carries a `Retry-After` header or an `errorCode`. A `503` whose `error` is `CREDENTIAL_UNVERIFIABLE` is not one of them: your API key could not be checked, so the request was not attempted and nothing was cancelled. `408` and the broker's `503` are lost-response cases: the orders may or may not have been cancelled, so re-read them before re-issuing.

## Cancel Sweep Response

`POST /api/v1/orders/cancel-all` and `POST /api/v1/orders/cancel-event` return `CancelSweepResponse` with a status of `200` or `207`.

<Warning>
The five market fields this response used to carry — `clearedMarkets`, `failedMarkets`, `notAdmitted`, `markets` and `cancelled` — were removed in `markets-v0.0.149`. `results` is the source for what became of your orders. See [Migrating from the market fields](/developers/orders#migrating-from-the-market-fields).
</Warning>

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `results` | `CancelSweepOrderResult[]` | Yes | One entry per order the request covered, across every market. Read this to learn what became of your orders. `[]` when nothing needed cancelling. |

`CancelSweepOrderResult`:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `orderId` | UUID string | Yes | Order UUID. |
| `success` | boolean | Yes | Whether this request cancelled the order. `false` does not by itself mean the order is still resting: an order that was already filled or cancelled when the request reached it is also `false`. Read `code`. |
| `code` | string | No | Machine-readable failure class when `success` is `false`. Branch on this rather than on `error`. |
| `error` | string | No | Human-readable detail. Do not branch on it. |

For each entry where `success` is `false`, act on `code`:

| `code` | Order still resting | Meaning |
| --- | --- | --- |
| `state-conflict` | No | The order was no longer open when the cancel ran. It was filled or cancelled first, or it left the book between Hit reading your orders and the venue reading its own. Look the order up if you need its final status. |
| `not-found` | No | No such order of yours exists. |
| `not-attempted` | Yes | Nothing was validated or written for this order. Re-sending is safe. |
| `engine-busy` | Yes | The venue declined to admit the cancel for this order's market. Re-send. |
| `unknown` | Possibly | The venue cannot say whether the cancel took effect. Read your open orders before re-sending. |
| Missing, or any other value | Yes | Treat the order as still resting. |

Entries carry no market ID.

| Status | Body | Meaning |
| --- | --- | --- |
| `200` | `CancelSweepResponse` | Every order in scope is off the book, either cancelled by this request or already gone when it arrived. |
| `207` | `CancelSweepResponse` | At least one order is still resting or may be, which includes a request in which nothing was cancelled. Those orders are the unsuccessful entries whose `code` is not `state-conflict` or `not-found`. If `results` holds none, read your open orders before re-sending. |
| `409` | Error | You already have a cancel in flight. Nothing was cancelled by this request, and the body carries no `results`. |
| `422` | `error: "CANCEL_SWEEP_TOO_MANY_TOKEN_PAIRS"` | The request covers more token pairs than one cancel request may. Nothing was cancelled, `results` is `[]`, and `tokenPairsRequested` and `tokenPairLimit` give the two figures. Cancel in smaller requests, by market or by event. Whether a limit applies is set per deployment, so handle this whether or not you have seen it. |
| `503` | `error: "ORDER_SERVICE_UNAVAILABLE"` | Hit cannot report on the request. Branch on `outcome`: `nothing-cancelled` means it never started, so re-send the identical request; `unknown` means it may or may not have cancelled, so read your open orders before re-sending. `results` holds any verdicts reached before the failure, so process them. Carries `Retry-After` and `retryAfterSeconds`. |
| `503` | `error: "ORDER_ADMISSION_UNAVAILABLE"` | The venue declined the command. Carries `errorCode`, `Retry-After` and `results`. See [Admission Errors](#admission-errors). |
| `503` | `error: "CREDENTIAL_UNVERIFIABLE"` | Your API key could not be checked, so the request was not attempted and nothing was cancelled. No `results` and no `Retry-After`. See [Authentication](/api-reference/authentication). |

Branch on the status first, then on `error`. Do not branch on `message`.

## Admission Errors

`POST /api/v1/orders` answers `503` when the order could not be signed, submitted or admitted. Every `503` on that endpoint means nothing was created, so re-sending the identical body cannot duplicate the order. Each of these responses carries a `Retry-After` header and repeats the same figure in the body as `retryAfterSeconds`.

A `503` whose `error` is `CREDENTIAL_UNVERIFIABLE` is not one of these. Your API key or JWT could not be checked, so the order was not attempted. It carries no `Retry-After` header and none of the fields below; see [Authentication](/api-reference/authentication).

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `statusCode` | integer | Yes | `503`. |
| `error` | enum string | Yes | `SIGNING_UNAVAILABLE` or `ORDER_ADMISSION_UNAVAILABLE`. This is the discriminator; read it before `errorCode`. |
| `errorCode` | enum string | No | Present only when `error` is `ORDER_ADMISSION_UNAVAILABLE`. |
| `message` | string | Yes | Error message. |
| `retryAfterSeconds` | integer | Yes | Seconds to wait before retrying. Repeats the `Retry-After` header. |

`SIGNING_UNAVAILABLE` carries no `errorCode`. It has four causes: the signing provider being unavailable, rate-limiting Hit or having no slot in Hit's signing-admission queue; the request budget being exhausted before the order could be submitted; the duplicate guard's store being unavailable; and, on `POST /api/v1/orders/batch` only, the locking infrastructure being unavailable. Three of those four — the request budget, the duplicate guard's store, and the batch locking infrastructure — reach orders you signed yourself, so this status is not limited to orders Hit signs for you. Every batch takes its per-account lock whether or not anything in it needs signing.

`ORDER_ADMISSION_UNAVAILABLE` carries an `errorCode`:

| `errorCode` | Meaning |
| --- | --- |
| `projection-stale` | The balance projection is not committing. |
| `balance-unknown` | Your balance has not been read from chain yet. |
| `balance-unprojected` | You have no projection row. |
| `collateral-source-unavailable` | The projection could not be queried at all. |
| `engine-busy` | The venue declined to admit the command at all. |
| `idempotency-unverifiable` | The venue could not check whether the idempotency key derived from your order had already been used. |

The first four mean your collateral could not be read. `engine-busy` is a stronger statement than the others: the command was not decided, not recorded and not partially applied, because the venue was at one of its own internal bounds. `idempotency-unverifiable` means the duplicate check could not be answered, so the venue refused rather than risk a second live order for one key.

For `engine-busy` and `idempotency-unverifiable`, re-send the identical body and do not change `salt`. The idempotency key is derived from the order's contents, so a new salt is a different order and defeats the deduplication.

None of these values means your order is invalid or your balance is insufficient. A genuinely insufficient balance is a `400`, and retrying it will not help.

`POST /api/v1/orders/cancel-all` and `POST /api/v1/orders/cancel-event` report a market the venue declined through `results`: every order in such a market that the venue had not yet decided carries `code: "engine-busy"`, and anything it decided before declining carries its own verdict. Other markets in the same request may have been cancelled, so re-send rather than assuming either way. `results` entries carry no `retryAfterSeconds`.
