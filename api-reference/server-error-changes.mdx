---
title: Server Error Changes
description: Trading API responses that changed from a 4xx to a 5xx on 25 November 2026, and what your client should do
---

Some failures on Hit's side used to be answered as if your request was wrong. Since **25 November 2026** they return a `5xx`, or a new per-order code, so your client can tell a fault it should retry from a request it should fix. Nothing about a successful request changed.

## What changed

### Reading a market

The endpoints in the table below now answer a failed read of a market with the `500` or `503` shown, instead of a `400`. These are all the documented endpoints that did so. Two documented endpoints that read markets are not in the table because they do not answer with an error: `POST /api/v1/orders/batch` answers `201` and reports the failure on the entry (see Orders below), and `GET /api/v1/profiles/by-name/{name}/summary` already answers `200` with `positionsValue` of `"0.00"` when it cannot read the markets of the positions, and did not change.

| Endpoint | Before | Since 25 November 2026 |
| --- | --- | --- |
| `GET /api/v1/markets/{id_or_slug}` with a slug | `400` with `message: "Error getting market by slug"` when the database failed | `500` with `message: "Internal server error"`, or `503` with `Retry-After: 1` when the server's database connections are all in use |
| `GET /api/v1/markets?ids=` | `400` with `message: "Error getting markets by IDs"` | The same `500` or `503` as above |
| `GET /api/v1/markets/{id_or_slug}/holders` and `GET /api/v1/markets/{id_or_slug}/users`, each with a slug | `400` with `message: "Error getting market by slug"` | The same `500` or `503` as above |
| `GET /api/v1/markets/user-positions`, `GET /api/v1/markets/value`, `GET /api/v1/events/{id}/positions` and `GET /api/v1/profiles/by-name/{name}/positions`, when the markets of the positions could not be read | `400` with `message: "Error getting markets by IDs"` | The same `500` or `503` as above |
| `GET /api/v1/order-book/book` and `GET /api/v1/order-book/last-trade-price`, when the token's market could not be looked up | `400` with a message starting "Error getting" | The same `500` or `503` as above |
| `POST /api/v1/orders`, when the order's market could not be read | `400` with a message starting "Error getting" | The same `500` or `503` as above |
| `GET /api/v1/price-history`, when the token's market could not be looked up | `400` with `message: "Error getting market by token id"` | `500` with `message: "Failed to fetch price history"`, or `503` with `Retry-After: 1` when the server's database connections are all in use |

`GET /api/v1/markets/{id_or_slug}`, `GET /api/v1/markets/{id_or_slug}/holders` and `GET /api/v1/markets/{id_or_slug}/users` with a UUID already answer `500` when the database fails, or `503` with `Retry-After: 1` when the server's database connections are all in use, and that did not change. `GET /api/v1/orders` and the other order reads were not part of this change.

### Orders

| Endpoint | Before | Since 25 November 2026 |
| --- | --- | --- |
| `POST /api/v1/orders/batch`, an entry Hit could not check because a read failed on its side, such as the market read or the wallet-code read, or any other server-side fault | For a failed market read, `code: "bad-request"` with `error: "Error getting market by token id"`. For a failed wallet-code read on an account whose wallet Hit has found changed outside the app and not yet restored (an earlier order was refused with `errorCode: "wallet-code-changed"`, or rejected at settlement with reason `wallet_code_changed`), `code: "wallet-code-changed"` with `error: "Your wallet was changed outside the app. Restore it to keep trading."`. For any other server-side fault, `code: "bad-request"` with the raw message of the failure | `code: "check-unavailable"`. For a failed market read, `error` is still "Error getting market by token id". For a failed wallet-code read, `error` is "Your wallet could not be checked just now. Send the order again.". For any other server-side fault, `error` is "Internal server error" |
| `POST /api/v1/orders` for an account whose wallet Hit has found changed outside the app and not yet restored (an earlier order was refused with `errorCode: "wallet-code-changed"`, or rejected at settlement with reason `wallet_code_changed`), when the wallet's code cannot be read | `400` with `errorCode: "wallet-code-changed"` | `503` with `errorCode: "wallet-code-unavailable"` and `Retry-After: 1` |

### Platform configuration and API keys

| Endpoint | Before | Since 25 November 2026 |
| --- | --- | --- |
| `POST /api/v1/trading/auth/api-key` when the signing provider rate-limits, is down or times out | `400` with "Signature required. Session signer not granted." (while reading the session signer), or a message built from the provider's error (while signing) that begins "Session signer signing rate limited:", "Session signer signing timed out:", "Session signer signing could not reach Privy:" or "Session signer signing failed upstream:" | `503` with `error: "SIGNING_UNAVAILABLE"` and a `Retry-After` header |
| `POST /api/v1/orders`, `POST /api/v1/trading/auth/api-key` and other endpoints, when Hit's own platform configuration is missing | `404` with "Entity not found." | `500` with `message: "Internal server error"` |

## What your client should do

- **A `503` this notice lists, on `POST /api/v1/orders`, `POST /api/v1/trading/auth/api-key` or a read endpoint:** nothing was created. Wait the number of seconds in the `Retry-After` header, then send the same request again. Some `503` answers carry no `Retry-After`, and the advice in this bullet does not apply to them: `CREDENTIAL_UNVERIFIABLE` (see [Authentication](/api-reference/authentication)); `ORDER_PLACEMENT_PAUSED`, with `message: "Trading is temporarily paused."`, which the order-placement routes answer while trading is paused; `GET /api/v1/price-history`'s "Price history could not be read."; and `GET /api/v1/order-book/last-trade-price`'s "Last trade price could not be read." None of these was part of this change. `SIGNING_UNAVAILABLE` and `ORDER_ADMISSION_UNAVAILABLE` on `POST /api/v1/orders` do carry one: see [Admission Errors](/api-reference/orders#admission-errors).
- **`POST /api/v1/trading/auth/api-key` is limited to 5 requests per hour.** Each retry of its `503` counts towards that limit, and once it is spent the route answers `429`. Retry it a few times at most, then wait.
- **`500`:** treat it as a fault on Hit's side. The request is not what is wrong, so do not change it. A `500` from a temporary database fault can succeed when you send it again, so retrying with a back-off is reasonable. If it keeps happening, report it to Hit with the time and the `path` from the response body.
- **`code: "check-unavailable"` on a batch entry:** nothing was created for that entry. Send that order again, on its own or in the next batch. The entry's `error` text is a short description, or `Internal server error` when the cause is not one it can name, so do not rely on it to say which read failed. A re-send often clears it, but not always: if the same order keeps coming back `check-unavailable`, report it to Hit.
- **`errorCode: "wallet-code-unavailable"`:** nothing was created. The body is `statusCode`, `message`, `errorCode` and `retryAfterSeconds`, with no `error` field, and `message` is "Your wallet could not be checked just now. Send the order again." Branch on `errorCode`, wait, and re-send the identical order. A `400` with `errorCode: "wallet-code-changed"` is unchanged: it means your wallet's code did change.
- **`error: "SIGNING_UNAVAILABLE"` from `POST /api/v1/trading/auth/api-key`:** no key was created. The `message` is "API key signing is rate limited; retry the request." or "API key signing is temporarily unavailable; retry the request." Wait for `Retry-After`, then request the key again. A user with no session signer still gets the same `400` as before.

If your client treats every `4xx` as "do not retry" and every `400` as "fix the request", update it to retry a `503` and to alert on a `500`. If it matches on the old messages, "Error getting …" or "Entity not found.", it no longer sees them for these failures, except that a batch entry for a failed market read keeps `error: "Error getting market by token id"`, now under `code: "check-unavailable"`.

See also [Errors](/api-reference/introduction#errors) and [Admission Errors](/api-reference/orders#admission-errors).
