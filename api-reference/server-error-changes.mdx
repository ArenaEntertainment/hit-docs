---
title: Server Error Changes
description: Trading API responses that changed from a 4xx to a 5xx, and what your client should do
---

Some failures on Hit's side used to be answered as if your request was wrong. They now return an honest `5xx`, or a new per-order code, so your client can tell a fault it should retry from a request it should fix. These changes take effect on **RELEASE DATE TO BE CONFIRMED**.

## What changed

| Endpoint | Before | Now |
| --- | --- | --- |
| `GET /markets/{id_or_slug}`, the order book read, `POST /orders` and other endpoints that read a market | `400` with a message starting "Error getting" when the database failed | `500` with `message: "Internal server error"`, or `503` with `Retry-After: 1` when the server's database connections are all in use |
| `POST /orders/batch` | An entry Hit could not check because of a failed market read or wallet-code read had `code: "bad-request"` or `"wallet-code-changed"` inside the `201` | That entry has `code: "check-unavailable"` |
| `POST /orders` for a wallet that was refused before, when its code cannot be read | `400` with `errorCode: "wallet-code-changed"` | `503` with `errorCode: "wallet-code-unavailable"` and `Retry-After: 1` |
| `POST /trading/auth/api-key` when the signing provider rate-limits, is down or times out | `400` with "Signature required. Session signer not granted." or the provider's own message | `503` with `error: "SIGNING_UNAVAILABLE"` and a `Retry-After` header |
| `POST /orders`, `POST /trading/auth/api-key` and other endpoints, when Hit's own platform configuration is missing | `404` with "Entity not found." | `500` with `message: "Internal server error"` |

## What your client should do

- **`503`:** wait the number of seconds in the `Retry-After` header, then send the same request again. Nothing was created.
- **`500`:** treat it as a fault on Hit's side. Do not change the request. If it keeps happening, report it to Hit with the time and the `path` from the response body.
- **`code: "check-unavailable"` on a batch entry:** send that order again, on its own or in the next batch. Nothing was created for it.
- **`errorCode: "wallet-code-unavailable"`:** the body is `statusCode`, `message`, `errorCode` and `retryAfterSeconds`, with no `error` field. Branch on `errorCode`, wait, and re-send the identical order. A `400` with `errorCode: "wallet-code-changed"` is unchanged: it means your wallet's code did change.
- **`error: "SIGNING_UNAVAILABLE"` from `POST /trading/auth/api-key`:** the `message` is "API key signing is rate limited; retry the request." or "API key signing is temporarily unavailable; retry the request." Wait for `Retry-After`, then request the key again. A user with no session signer still gets the same `400` as before.

If your client treated every `4xx` as "do not retry" and every `400` as "fix the request", update it to retry a `503` and to alert on a `500`. If it matched on the old messages, "Error getting …" or "Entity not found.", it will not see them for these failures any more.
